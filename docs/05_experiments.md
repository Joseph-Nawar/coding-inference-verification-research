# 05 — Exploratory experiment portfolio

These are concrete initial designs, not a frozen confirmatory plan. Lock each stage's inputs, endpoints and resource caps before running; revise only by logged amendment. All experiments use development tasks only after P0/P1 approval. No new algorithm is presupposed. Do not run all branches automatically if the preceding stage exposes a problem.

## E1 — Shared candidate bank (H1, H3, H6)
40 dev tasks (20 each benchmark), 8 independent stochastic generations per task, one model. Fixed prompt: solve task in Python, return complete function/code, no discussion. Apply actual tokenizer chat template; record raw text, deterministic extraction and cleaned code. No LLM-assisted extraction, retries for bad code or sampling until success. Stable seed per task/model/index; default temperature .7, top_p .95, max_new_tokens 768; P1 can justify pre-E1 adjustment. Candidate 0 is a stochastic single attempt (greedy separately optional, not the same estimand). Retain duplicates, invalid and truncated candidates. Run V and D with independent trusted comparator, then freeze pool and selection decisions before joining Y/H in analysis. H scores must not be visible to any subsequent model call.

Compare k=1,2,4,8 nested prefixes: first, uniformly random (analytic fraction correct in pool), visible-test pass count (ties smallest index), behavior consensus on V (largest cluster by qualified typed output signature; ties deterministic; report missing/incompatible signatures), oracle-any(Y). Also evaluate base acceptance vs Y and H. Report pass@k unbiased estimator only for fixed n>=k and labeled stochastic samples; distinguish empirical prefix-any from estimator. Report duplicates, number of mixed-correctness behavioral clusters, oracle headroom, selection headroom, model/infra failures, test strength. Do not use gold to choose consensus or tie-break. This is not CodeT/S* reproduction.

## E2 — Evidence versus interpretation (H1/H3)
Use first 4 of the same E1 candidates, not best 4. First 24 eligible dev tasks by prelocked hash order, ideally 12 per benchmark. Same candidate order/permutation across conditions, randomized deterministically by task independent of correctness. Same model, one call per arm, output candidate index only, max 128 output tokens, no retries, fixed context cap. A: task + candidate code; B: A + V per-candidate pass/fail summary; C: B + identical D inputs and candidate outputs/status (no expected output); D: C + valid D expected outputs/comparison results (oracle-assisted). Use one fixed prompt skeleton, canonical row order, uniform output formatting and predeclared truncation; if not representable within context, mark all four arms ineligible together before selection labels. Report input tokens/latency; equal calls do not imply equal compute. Include deterministic V and V+D pass-count selectors, random and oracle-any for k=4. The D deterministic selector is essential: if even valid evidence leaves mixed pools unresolved, don't blame the LLM. If valid D separates correct candidates but selector still misses them, interpretation is plausible; distinguish ranking vs ties, incorrect verdict vs invalid output. A wrong selection with a correct candidate available is not necessarily a reasoning failure if evidence is ambiguous. Record conditional accuracy on mixed pools, visible signatures that contain both labels and evidence coverage. D may not identify true correctness; no causal claim about latent model reasoning. Label any conditional gold analysis retrospective. If few mixed pools, report sparse denominator, expand only with new documented dev sample or adjust future model; don't abandon program.

## E3 — Repair context × feedback (H2, H4, H5)
Use candidate index 0 per task from E1 (not oracle-selected). Eligible for primary factorial if V supplies a valid reproducible failing counterexample, including complete expected and actual outcomes or typed exception; do not use H/Y to select cases. Up to 24 eligible tasks in prelocked hash order. Four independent branches, same initial problem and max 768 output tokens, matched sampling parameters/seeds by task and replicate, fixed prompt skeleton:
- R00: problem only (fresh sample).
- R10: problem + initial code, ask for revised full solution, no diagnostic feedback.
- R01: problem + first V failure (input, expected, observed, status), no initial code.
- R11: problem + initial code + identical failure packet.
The feedback packet must omit original code/source snippets in R01; note that observed outputs may indirectly reveal behavior. Do not fabricate feedback or use gold. Compare context effect at both feedback levels, feedback effect at both context levels and difference-in-differences. Score V/H/Y only after branch generation is frozen. One call per arm is a matched action comparison, not matched FLOPs; report tokens and cost. Include original candidate as no-op baseline. Limit R00/R10/R01/R11 to one stochastic attempt each initially. Failures retained; do not silently retry. If sample small, report descriptive results with uncertainty; no confirmatory significance claim.

H5 separate preservation panel: up to 16 base-pass initial candidates (candidate 0, hash order, no gold filtering), generate R10 unconditional revision once, compare original vs revised Y/H; also simulate retain-if-V-score-not-worse vs unconditional revise, explicitly describe tie policy. Retrospectively partition by Y(initial) to measure regressions/repairs. Do not tell model initially correct. V-pass is not true correctness. Never expose H verdict to gate. Record parse, syntactic and runtime transitions, visible test changes. Distinguish retention policy effects from revision effects.

If E3 yields informative feedback gains, next exploratory follow-up may compare fixed-count equally valid diverse vs redundant failure packets (matched input/output token budget and counterexample count) or verified runtime observations, using new predeclared dev panel. Use output-behavior diversity, not unsupported inferred bug taxonomy. This follow-up is not initially authorized.

## E4 — Test discrimination × label validity (H3)
Use shared E1 fixed candidate pools and V/D panels; up to 24 eligible tasks, hash order. Initially use valid benchmark D inputs; ask model to predict expected outputs on these inputs without candidate code (one structured call per task, max 512 output tokens). Separate condition optionally includes a candidate, if later approved. These are model-generated expectations on fixed valid inputs, NOT fully generated test suites. Compare asserted outputs against official comparator/reference, retain parse-invalid labels, unsupported alternative-output cases and errors. Never execute model-generated assertions on host. An independent model/family or prompt can later test dependence. Generated inputs may be explored only with validated domain constraints and oracle semantics; reject unsupported cases, log selection; no assumption that arbitrary syntactically valid input is in specification.

For each pool, build high- and low-discrimination panels of equal size (default 2 inputs) using observed candidate-output partition diversity only, no Y/H. Use a predeclared entropy/pair-separation metric; deterministic tie break, disjoint panels where feasible. If insufficient variation, record no contrast. For each panel evaluate predicted expected outputs vs oracle-valid expected outputs on same inputs. For invalid model predictions, compare behavior under a strict no-evidence policy vs treating parse-invalid test as rejected, predeclare one primary. A controlled label corruption (valid alternative wrong label, no ambiguity) can later isolate validity independently, but is not a model-generated error. Compare selection (deterministic pass-count, ties index) and false accept/reject against Y/H; report discriminator strength, test validity, overlap of rejected correct/accepted incorrect candidates and paired evidence. Do not claim shared causal misconception solely from correlation; candidate-level dependence requires comparison to matched independent verifier or perturbation, controlling task difficulty. Selection gain from oracle labels is diagnostic upper bound. E4 first asks whether the mechanism is measurable, not whether a new method wins.

## E5 and beyond (not authorized)
Depending on results: test feedback diversity, natural correlated error with independent verifier and same task/pool, candidate-context effects using controlled alternative code, budget curves, or second-model replication (same task IDs, prompts, quantization recorded). Before follow-up register question, rival explanations, cost, evidence that would change decisions, and outcome access. After exploratory cap, assess literature and select a consequential claim. Confirm on sealed tasks/new benchmark with strong closest-work baseline(s), additional model families and prespecified primary contrasts, uncertainty and practical effect sizes. Full S*/CodeT/PATSSEL reproduction may be necessary for a method claim, not for initial diagnostics.
