# 03 — Data, split, information and correctness contract

## Task universe and split
Use pinned EvalPlus full HumanEval+ and MBPP+ releases (not mini/noextreme unless explicitly amended). Audit actual versions, IDs, task counts, schemas, licenses, reference behavior, prompt format, entry point, task-specific comparison, base_input and plus_input. Stable sort within each dataset by SHA-256 over the private split namespace, dataset version and task ID. Select 4 tasks/dataset smoke (8), next 20/dataset development (40), next 40/dataset reserved confirmation (80), remaining tasks reserve. No result-driven task swaps or excluding difficult tasks. This is a deterministic random-like split by benchmark, not a difficulty-stratified sample. Audit exact duplicate prompts and cross-benchmark near-duplicate risks before lock; if duplication forces grouping, record revised deterministic rule before outcome access. Mark ineligible unsupported semantics based only on preflight criteria; retain all and report counts. Confirmation tasks are only ID/hash commitments at this stage; do not generate, score or inspect their detailed test contents during exploration. Public benchmarks are not genuinely secret from pretrained models; call them workflow-held-out, not contamination-free.

## Evidence partition (per smoke/dev task)
- P: task statement, signature, prompt-provided examples. Do not append canonical solution, plus tests or evaluator labels.
- V: official base inputs with benchmark-valid expected outputs, used in visible selection and feedback. The generation prompt initially receives P only. Report overlap between P examples and V if identifiable.
- D: dedicated diagnostic input panel, sampled deterministically from plus inputs after exact typed-input deduplication against V and within plus. Up to 8 inputs, retain at least 8 unique withheld inputs H to qualify for D/H experiments. If not enough, flag task as ineligible for D/H only; do not drop from E1. Use stable typed serialization, avoid lossy list/tuple/set collapse. No gold-based choice of D. Special comparators and input domain matter; use the official valid inputs rather than asking an LLM to invent invalid ones initially.
- H: remaining unique plus inputs; never expose to generation, repair, test generation, selection or prompt construction. H is independent of the diagnostic panel in the workflow sense, not necessarily behaviorally independent. Use H only in scorer/analysis after candidate/selector results are frozen. In development, H results may guide researcher exploration across tasks, never same-run candidate decisions. Reserved confirmation tasks are untouched until a separate plan is locked.

## Correctness
Primary operational label Y = passes full pinned official base+plus protocol (including timeouts, special oracles, tolerance, types, allowed alternatives and official execution semantics). Separately record H-only pass and V/D scores for eligible tasks. V and D are parts of the official score; H-only and later new task results distinguish improvement on exposed vs unexposed inputs. Do not call any finite test set proof. A disagreement on output does not imply one is wrong if multiple outputs satisfy the contract. A task with no meaningful behavioral signature comparator is ineligible for signature-based analyses only, not automatically a failure or exclusion from official score.

Pin official evaluator, use `base_input`, `plus_input`, `canonical_solution`, `entry_point`, `atol`, special-oracle code and official time-limit semantics. Validate trusted reference results independently using official scorer. Do not treat string equality/JSON equality as ground truth. Official scorer requires a solution for each task in some versions: adapt subset invocation only with a checked wrapper and parity tests, not hidden silent patches. Record reference times and timeout sensitivity. Candidate runner produces typed results/exception/timeout without expected labels; trusted comparator determines outcome. For incompatible mutation/stateful/alternative-output tasks, either implement faithful safe semantics and verify parity or restrict specific analysis by preregistered eligibility; official score must preserve semantics or be reported as unavailable. Do not execute arbitrary pickle, eval, or deserialization code on host.

## Boundaries
Generation and selection process sees only allowlisted prompt/evidence JSON, never reference implementation, H, final-task IDs beyond needed manifest or gold per-candidate correctness. Separate evaluator/analysis artifacts from generation workspace; manifest hashes and access counters; use a separate execution/evaluation process and explicit schema with deny-by-default keys. Oracle diagnostics D expected outputs are reference-assisted, not available for ordinary deployable tasks. Base expected outputs likewise benchmark-assisted. No test label leaks via caches, exceptions, logs, retries, selector prompts, or model-directed scoring. D evidence and V are explicitly recorded on each call. Use hashes, tests with canary labels, and prompt inspections. This is a research workflow boundary, not a claim that someone with full local disk permissions cannot read data.
