## Implementation and security evidence

The candidate image contains Python, the worker and the typed transport. The distinct trusted fixture image contains the reference helper and checker. Each production base or plus panel uses one fresh candidate process. The host sends only source, entry point, one input and its authorized timer at a time. This preserves ordered function state without opening the rest of the panel. The decoder has frame, nesting and node bounds, rejects executable objects and verifies schemas. Malformed responses, unsupported types, output limits, and supervisor exhaustion yield unavailability. Syntax errors, ordinary execution exceptions and worker timer expiry have separate statuses. A separate scorer replays bounded validated replies only after removing the candidate container, so verdicts and comparison work do not influence the candidate's next input.

The final 20 automated tests passed under the production profile. The tests verified only loopback was up, denied egress and DNS, expected UID and effective capabilities, Docker seccomp and no-new-privileges, worker denial of child executable launch, no host mounts or socket, read-only root and writable tmpfs, runtime memory and process cgroup limits, ordered delivery, no queued future input, clean state across panels, and label-canary exclusion. They exercised malformed frames, Python and native output bounds, wall expiry, cleanup by container ID, and rejection of a second simultaneous production runner. The macOS offline canary separately verified kernel-denied network access and denied reads of a protected path. Docker is the production containment boundary. Candidate data from its own result stream is still untrusted.

## Official semantic parity and limitations

- All 14 authored synthetic panels matched the patched official checker, including alternate roots, typed and floating results, MBPP special oracles, exceptions and timeouts, ordered state and mutation. The regression from v1 remains preserved. Production fixtures separately exercised malformed candidate code and invalid responses.
- All 32 separated smoke-fixture panels matched the official verdict and full test detail vectors for independently authored correct and incorrect programs. This is 7,010 per-case comparisons across 3,505 registered cases. The sequential post-removal scoring run took 21.89 seconds including the official comparisons. All fixture case values and task membership remain private.
- The transport supports exact builtins used in the smoke fixtures. Arbitrary classes, ndarray results, cycles, aliases requiring object identity across the trust boundary, and non-representable outputs remain unsupported. Out-of-protocol representations yield an unavailable evaluation. The smoke fixtures required no case removals.
- A synthetic case demonstrates that EvalPlus can accept a root by comparing against candidate-mutated coefficients. The separated comparator reproduces the verdict from reported post-call values. This is parity for that case. The worker cannot guarantee adversarial integrity of its own state reports, and the oracle is sensitive to mutation by design. The eight smoke tasks have no mutation-sensitive special oracles. Qualify such cases prospectively before broader evaluation. The separate canonical-reference problem in upstream issue #334 also needs prospective qualification before confirmation. No confirmation records were decoded to investigate it. [Upstream issue](https://github.com/evalplus/evalplus/issues/334)
